# Patterns to reuse for later games

These lessons come from KH1FM implementation and its corrective review, not just the original design proposal.

## Preserve four different kinds of state

Canonical game facts are authored, sourced records. Each game has a separate persistent Chroma database, and the browser receives its exported vectors and metadata. Player checks, stock and plans belong in IndexedDB. Shared downloaded model weights belong in the browser model cache. Questions, answers and follow-up context belong only in memory. Never seed player activity, conversation, source-audit TODOs or another game's records into a Coppermind.

Chroma itself writes `chroma.sqlite3`. That filename does not mean the legacy game SQL schema was reused or that the phone needs a SQL server. Use one `PersistentClient` path per game; collections alone do not meet the required isolation.

## Normalize identity before presentation or embeddings

Keep stable canonical IDs across compact rows, inline details, search, planner links and citations. Model actual acquisition events explicitly: two rewards granted together should toggle and undo atomically, while opening a chest generated by another action can remain a distinct acquisition. Grouped puppies count as one acquisition with three recovered units. Compute denominators from the agreed unit rather than adding every visible row.

Use checked-in factual snapshots plus repeatable importers, with an audit disposition for each candidate source row. Reconcile modern-version replacements and independent inventories. Source-backed does not imply hands-on verified. Preserve a narrow uncertainty rather than converting agreement elsewhere into confidence about the disputed field.

## Keep arithmetic outside the assistant

The September 20 refinement supersedes the old recipe-queue UI. Workshop tabs are Recipes → Materials → Farming Plan. Inventory controls are always present; blank stock means unknown, never zero. A recipe addition contributes its direct ingredients for one craft to persistent material targets; repeat additions accumulate and shared ingredients use one target. Direct material additions establish a target without overwriting an existing one. Remaining is max(target − owned, 0), and removing a target preserves stock. Historical crafted checks never consume inventory.

Keep the legacy deterministic planner for its existing callers, but do not confuse its selected-output/first-craft modes with the manual farming-target interface. Craftable ingredients expose their requirements and farming details inline without silently expanding the target list. Only selected alternatives contribute ingredients. Numerical logic and validation belong in application code, not generated prose.

## Carry forward the refinement decisions

Use the [refinement playbook](refinement-playbook.md) as the current presentation contract. Lead with a descriptive title and useful counts; remove advertising-style eyebrow/title/subtitle stacks. Keep readable text, compact spacing and the journal palette. Organize primary navigation by collectible/category, with world hubs linking to filtered category views. Single-column expandable rows replace nested item pages; checks operate separately, multiple rows stay open and category controls expand/collapse all. Backup alternatives are compact modals or category tables, not the default.

Materials show source, percentage or “Conditional,” farming location, owned stock and Add to farming plan when collapsed. Expanded rows hold specific rules and finite alternatives. The farming plan contains all those details inline. Use distinct menu icons and preserve real character/edition boundaries. No Data Jiminy work is part of this cross-game rollout; earlier model-specific lessons below describe existing KHFM architecture, not authorization to extend it.

## Treat persistence failures as product behavior

Apply mutations atomically against the latest stored revision, broadcast updates across tabs, preserve import recovery and guard undo against unrelated later writes. An awaited mutation is not necessarily a successful save if the store deliberately resolves failures after rolling back. Use the store's save/error state as the authoritative announcement; do not show an unconditional success toast afterward.

## Prove offline behavior by reopening it

A registered or active service worker is not proof of populated caches. The first KH1FM offline test found an active worker with an empty cache; inlining the Workbox runtime fixed that build. Test a cold offline reload of the production bundle. For models, reopen cache-only and run real encoder and generator probes before reporting readiness. Model delivery fixtures may supply actual pinned weights to a browser test, but disclose that this is not live CDN or physical-phone validation.

Pin embedding model revision, dtype, pooling, normalization and dimensions on both seed and query paths. Reject over-budget chunks before writing to Chroma; do not silently truncate prerequisites. Validate game/content version and corpus membership before retrieval. Preserve qualifiers in generated answers as well as prerequisites. Small-model output must pass an evidence check; prompting alone is not a factuality boundary.

## Design deployment paths into the runtime

Derive WASM assets from the owning document's deployment base, never the hashed worker URL. Test `/kh-tools/` as well as `/`. GitHub Pages publishes the built `dist` artifact, not the TypeScript source tree. Deployment follows pushes/merges into `master`; review branches run validation without publishing. Check the committed retrieval pack against canonical data before releasing so content changes cannot silently ship stale vectors.

## Review the actual responsive geometry

Fixed assistants need reserved space. KH1FM reserves a desktop rail and a mobile bottom dock; the mobile journal has one explicit scroll owner. Route restoration must follow that scroll owner. Keep inputs at least 16px, controls at least 44px and quiet text readable against paper. Inspect original artwork rather than inferring its identity from a filename. Keep optional media absent when there is none; synthetic fixtures validate maps, fallback and zoom without inventing production screenshots.

Use an independent corrective reviewer, then inspect the revised screens and integration yourself. Keep concurrent browser output directories separate: Playwright clears its output directory and can delete another runner's active traces. Desktop and phone-size Chromium emulation cannot certify iPhone 17 Safari, keyboard, VoiceOver or memory behavior.

Research provenance and player navigation serve different readers. Keep external research citations in maintenance records/docs; visible assistant references should point to the app’s own canonical entries. Do not expose source-row IDs, import audit fields or platform API placeholders as gameplay facts. Preserve useful uncertainty without turning each journal page into a research report.
